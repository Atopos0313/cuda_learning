# CUDA 学习归档规范

> 本规范用于每个 Day 结束后的知识整理。目标是让实验代码、原始数据、原理分析和最终结论能够按天查阅、复现和长期积累。

## 1. 目录结构

每个 Day 在 `doc` 下建立一个补零后的独立目录：

```text
doc/
├── ARCHIVE_CONVENTION.md
├── day01/
│   ├── README.md
│   ├── day01_*.md
│   └── day01_*.csv
├── day02/
│   ├── README.md
│   ├── day02_*.md
│   └── day02_*.csv
└── dayNN/
    ├── README.md
    ├── dayNN_*.md
    └── dayNN_*.csv
```

统一使用 `day01`、`day02`、`day10`，避免 `day10` 排在 `day2` 前面。

## 2. 每个 Day 必须包含的内容

### `README.md`

作为当天总入口，至少记录：

1. 学习主题和实验目的；
2. 实验原理；
3. 实现步骤；
4. 当天涉及的代码文件及职责；
5. 构建和运行命令；
6. 指标含义与判断标准；
7. 核心实验结果；
8. 正确性和性能分析；
9. 遇到的问题、原因和修复；
10. 最终结论、局限和下一步。

### 专题 Markdown

当一天包含多个阶段、多个实验或较复杂知识点时，拆成多个聚焦文档，例如：

```text
day06_part1_naive_analysis.md
day06_part2_tiled_analysis.md
day06_part3_padded_analysis.md
```

`README.md` 只做总览和索引，不堆放所有细节。

### CSV 结果

当天最终 benchmark CSV 与 Markdown 放在同一目录：

```text
doc/day06/day06_transpose.csv
```

CSV 至少保留：

- 实验版本；
- 输入规模；
- 预热和计时次数；
- Kernel 时间；
- 吞吐量或有效带宽；
- 正确性；
- 误差与首个错误位置。

统一使用 UTF-8 编码，便于 Git diff、编辑器和跨平台工具读取。

## 3. 代码与文档的关系

CUDA 源码继续保存在工程目录：

```text
include/
kernels/
benchmarks/
```

Day 目录不复制源码，而是在 `README.md` 中链接真实代码并说明职责。这样可以
避免文档副本与工程代码不一致。

代码文件分为：

- 当天新增或修改的核心文件；
- 当天复用的公共组件；
- 构建配置入口。

## 4. 每个实验的固定学习流程

```text
实验目的
→ 实验原理
→ 分步骤引导编写代码
→ 用户运行 Release benchmark
→ 保存原始 CSV
→ 解释每个指标
→ 分析正确性、性能和异常
→ 总结能证明与不能证明的内容
→ 写入当天 Day 目录
```

核心代码由学习者亲自编写；指导过程负责拆解步骤、解释原理、检查实现和分析
结果。性能实验直接接入 benchmark，但 benchmark 内必须保留 CPU reference
和 `PASS/FAIL` 正确性检查。

## 5. 结果分析要求

不能只给出“更快”或“更慢”，每次至少回答：

1. 每个指标是什么意思、单位是什么；
2. 指标越高还是越低越好；
3. 正确性是否通过；
4. 相对基线提升或下降多少；
5. 不同数据规模为什么表现不同；
6. 实验结果是否符合原理预测；
7. 哪些结论由数据直接支持；
8. 哪些原因只是可能解释、仍需 profiler 验证；
9. 当前瓶颈和下一步实验是什么。

## 6. 命名规则

```text
目录：       dayNN
总览：       README.md
专题分析：   dayNN_partN_<topic>_analysis.md
最终数据：   dayNN_<benchmark>.csv
```

文件名使用小写英文、数字和下划线；文档标题和正文使用清晰中文。

- [ ] 已保存 UTF-8 CSV

- [ ] 已链接专题分析文档和原始数据
