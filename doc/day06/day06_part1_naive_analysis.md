# Day 6 第一部分：Naive 矩阵转置结果分析

> 归档位置：`doc/day06/`；原始数据见同目录 `day06_transpose.csv`。

## 1. 本阶段要回答的问题

Day 6 第一部分不是为了立刻得到一个很快的转置 Kernel，而是先建立一个可信的
`naive transpose` 基线，并用实验回答：

1. Kernel 算出的转置结果是否正确？
2. 大矩阵下性能能否稳定？
3. Naive 转置的瓶颈在哪里？
4. 后续为什么需要 shared memory？

本节只分析同目录 `day06_transpose.csv` 中的 `naive` 行，暂不讨论 `tiled` 结果。

## 2. 原始结果

## 3. 每一个指标是什么意思

### `variant`

Kernel 版本名称。这里的 `naive` 表示每个线程直接：

1. 从输入矩阵读取一个元素；
2. 把它写到转置后的位置。

它没有借助 shared memory 重新排列数据。

### `height` 和 `width`

输入矩阵的行数和列数。输入是 `height × width`，输出是
`width × height`。

同时测试方阵和非方阵非常重要。只测试方阵可能掩盖把 `height`、`width`
写反的索引错误。

### `elements`

矩阵元素总数：

```text
elements = height × width
```

例如：

```text
2048 × 2048 = 4,194,304 个 float
```

### `warmup`

正式计时前执行 20 次 Kernel。

预热的作用是减小首次执行时 CUDA 上下文、缓存状态、时钟状态等因素对结果的
干扰。预热结果不计入最终时间。

### `iters`

正式测量 50 次。程序不是只看其中某一次，而是对 50 个时间样本取中位数。

### `kernel_ms_median`

50 次正式测量的 Kernel 时间中位数，单位是毫秒。数值越小越好，但只能在
“相同输入规模、相同工作内容”下比较。

使用中位数可以降低偶发系统抖动对结果的影响。

例如 `4096 × 4096` 的：

```text
0.816448 ms = 816.448 μs
```

### `GB_per_s`

这是有效带宽（effective bandwidth），表示 Kernel 每秒完成了多少“有用数据”
的读取和写入。

转置对每个 `float`：

```text
读取 input：4 Byte
写入 output：4 Byte
合计：       8 Byte
```

所以：

```text
有效带宽
= elements × 8 Byte / kernel 时间
```

以 `4096 × 4096` 为例：

```text
有用数据量
= 16,777,216 × 8 Byte
= 134,217,728 Byte

有效带宽
= 134,217,728 / 0.000816448
≈ 164.39 GB/s
```

这里采用十进制单位：

```text
1 GB = 1,000,000,000 Byte
```

必须注意：有效带宽不是显存总线上的真实流量。它只计算算法必需的 1 次读和
1 次写。Naive 转置的不合并写入会产生额外内存事务；这些额外流量没有进入
分子。因此，有效带宽适合比较算法版本，但不能直接当成显存控制器的真实
利用率。

### `correct`

GPU 输出与 CPU reference 是否一致。

`PASS` 才允许继续讨论性能。一个错误但很快的 Kernel 没有优化意义。

### `max_abs_error` 和 `max_rel_error`

分别是最大绝对误差和最大相对误差。

本实验只复制 `float` 的位模式，没有加减乘除，因此正确结果应当精确一致：

```text
max_abs_error = 0
max_rel_error = 0
```

这里所有结果都是 `0.00e+00`，符合预期。如果转置实验中出现很小但非零的
误差，也不应简单归因于浮点误差，而应优先检查索引、越界或数据覆盖。

### `first_mismatch`

若结果错误，它记录第一个不一致元素的线性下标；`none` 表示没有发现不一致。

## 4. 怎样判断这些结果好还是不好

### 正确性：好

五种尺寸全部 `PASS`，且误差为零：

- `3 × 5` 验证极小非方阵；
- `17 × 19` 验证尺寸不是 block 整数倍时的边界判断；
- `1003 × 769` 验证较大、不规则非方阵；
- 两个大方阵用于观察稳定性能。

因此可以确认当前索引映射和边界判断在这些测试范围内正确。

这不是数学证明，也不能保证所有可能尺寸都正确，但它已经覆盖了本阶段最重要
的边界类型。

### 小矩阵的性能数值：不能用来判断 Kernel 好坏

`3 × 5` 和 `17 × 19` 的时间都约为 4 微秒。真正搬运的数据极少，固定的
Kernel 启动、调度和计时开销占主导，所以算出的带宽只有 `0.03 GB/s` 和
`0.60 GB/s`。

这不表示 GPU 搬运小数据的显存速度真的这么低，而是：

```text
总时间 ≈ 固定开销 + 极少的数据处理时间
```

当分子几乎为零而固定时间仍存在时，计算出的 GB/s 必然很小。

因此小尺寸主要用于查正确性，不用于评价带宽。

### 大矩阵性能：稳定，但明显受限

`2048 × 2048` 与 `4096 × 4096` 的元素数量相差 4 倍：

```text
16,777,216 / 4,194,304 = 4
```

时间约增加：

```text
0.816448 / 0.208912 ≈ 3.91 倍
```

时间接近随数据量线性增长，而有效带宽从 `160.62` 稳定到 `164.39 GB/s`。
这说明规模已经足够大，固定启动开销被摊薄，Naive Kernel 进入了相对稳定的
吞吐区间。

当前 GPU 被识别为 GeForce RTX 2080 Ti。参考规格的理论显存带宽是
`616 GB/s`。`164.39 / 616 ≈ 26.7%`，说明 Naive 转置的有效带宽只相当于
理论峰值的约四分之一。

这个比例只能作背景参照，不能叫作精确的“硬件利用率”，因为：

1. `616 GB/s` 是理论峰值，真实程序通常达不到；
2. benchmark 的 `164.39 GB/s` 是有效带宽；
3. 不合并写入造成的额外真实流量没有计入有效带宽。

不过，约四分之一的结果与 Naive 转置存在严重写入浪费的判断是一致的。

## 5. 为什么 Naive 转置慢

一个 block 使用 `32 × 8` 个线程。在线程的 x 方向，一个 warp 的 32 个线程
读取同一行的连续元素：

```text
input[row][0]
input[row][1]
...
input[row][31]
```

每个 `float` 是 4 Byte，因此一个 warp 请求连续的 128 Byte。这样的读取容易
合并成少量内存事务，读取侧是友好的。

转置后，同一 warp 写入：

```text
output[0][row]
output[1][row]
...
output[31][row]
```

在线性内存中，相邻线程的写地址间隔是：

```text
height × sizeof(float)
```

以 `height = 2048` 为例，相邻线程地址相隔：

```text
2048 × 4 Byte = 8192 Byte
```

也就是说，32 个线程虽然总共只写 128 Byte 有用数据，但这些数据分散在跨度
很大的地址范围内，硬件难以把它们合并成少量连续写事务。

因此 Naive 版本的核心特征是：

```text
全局读取：连续、合并
全局写入：跨步、不合并
```

这就是性能稳定在约 `164 GB/s`、远低于连续访存实验的主要原因。

## 6. 从数据中能得出的结论

1. Naive 转置在所有已测尺寸上结果正确。
2. 小尺寸的 GB/s 主要反映固定开销，不能用来评价显存效率。
3. 从 `2048 × 2048` 开始，有效带宽稳定在约 `161～164 GB/s`，基线可信。
4. 大矩阵的执行时间近似随元素数量线性增长，说明它已进入稳定吞吐区间。
5. 瓶颈不是转置公式本身，也不是浮点计算，而是输出侧跨步写入造成的内存事务
   浪费。
6. 下一阶段 shared-memory tiled 转置的目标不是减少元素数量，也不是减少
   必须读写的 8 Byte/元素，而是重新组织访问顺序，使全局读取和全局写入都
   尽量连续合并。

## 7. 本阶段一句话总结

> Naive 转置“算得对，但写得散”：它的读取已经合并，跨步写入却浪费了大量
> 全局内存事务，因此在大矩阵上只能达到约 `164 GB/s` 的有效带宽；shared
> memory 的价值是充当 block 内的数据重排站，让全局内存两端都能连续访问。
